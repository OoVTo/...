1.1 Describe principles of responsible AI

The six Microsoft responsible AI principles

PrincipleMeaningTypical example
FairnessAI systems treat all people equitably and do not affect similarly situated groups differently.A loan model gives comparable approval rates to equally qualified applicants of any gender or ethnicity. Assess and mitigate bias in data and model.
Reliability and safetySystems perform consistently under expected and unexpected conditions and fail safely.Rigorous testing and monitoring of an autonomous vehicle or a medical triage bot; safe behavior with unusual inputs.
Privacy and securityProtect personal and confidential data; resist attacks; follow consent and data regulations.Encrypt data at rest and in transit, limit access with RBAC, minimize data collected, honor consent, redact PII.
InclusivenessEmpower and engage everyone, including people with disabilities and diverse backgrounds.Captions, screen-reader support, speech interfaces, multi-language support, diverse user testing.
TransparencyPeople can understand what a system does, how it reached a result, and its limits.Telling users they are talking to AI, publishing transparency notes, model cards, explainability, disclosing confidence and limitations.
AccountabilityPeople are answerable for AI systems; governance and human oversight exist.Defined owners, review boards, audit trails, human-in-the-loop for high-impact decisions, compliance with regulation.
Memory aid. The first four (Fairness, Reliability and safety, Privacy and security, Inclusiveness) are the ideals; Transparency and Accountability are the foundations that support them.

Responsible generative AI

Generative models add new risks. Microsoft's approach is a four-stage cycle:

  1. Identify potential harms (for example by red teaming and use-case analysis).
  2. Measure how often harmful or ungrounded output occurs with test sets and evaluations.
  3. Mitigate at multiple layers (below).
  4. Operate the solution responsibly: deployment readiness review, monitoring, incident response, user feedback, ongoing updates.

Mitigation layers

LayerWhat it covers
ModelChoose an appropriate model; fine-tune; use models with built-in safety training.
Safety systemPlatform-level controls: content filters, abuse monitoring, Azure AI Content Safety, Prompt Shields, groundedness detection, protected-material detection.
System message and groundingMetaprompt defining behavior and boundaries; grounding responses in trusted data (RAG).
User experienceDisclosures that content is AI-generated, limits on input length, human review, feedback buttons, citations.

Harms and tools to know

  • Harmful content categories in Azure AI Content Safety: hate and fairness, sexual, violence and self-harm. Each is rated by severity (safe, low, medium, high), and thresholds are configurable.
  • Hallucination / ungrounded content: fluent output not supported by source data. Mitigate with grounding (RAG), clear system messages, citations and groundedness detection.
  • Jailbreak and prompt injection: user (direct) or document (indirect) text that tries to override instructions. Prompt Shields help detect both.
  • Protected material detection: flags output matching known copyrighted text or code.
  • Content filters in Foundry are configured and attached to model deployments and apply to prompts and completions.
  • Transparency Notes describe a service's intended uses, capabilities, limitations and best practices. Limited Access gates sensitive capabilities (for example some face and custom voice features).
  • Responsible AI dashboard (Azure Machine Learning) supports fairness, error and interpretability analysis for traditional ML models.
  • No filter is perfect: layered defenses plus human oversight are required.

1.2 Identify AI model components and configurations

Core concepts

  • Artificial intelligence: software that mimics human abilities such as perception, language and decision-making. Machine learning learns patterns from data. Deep learning uses multi-layer neural networks. Generative AI creates new content.
  • Features are the input variables (x); the label is the value to predict (y). Training fits a model to data; inference uses the trained model on new data.
  • Data is split into training, validation and test sets. Overfitting = excellent on training data, poor on new data. Underfitting = poor everywhere.
Outline focus. The official 1.2 skills are: describe how generative AI models work, identify an appropriate model based on capabilities, and identify appropriate deployment options and configuration parameters. Classic machine learning below is general background.

Evaluation metrics Beyond the outline

Regression

  • MAE: mean absolute error
  • MSE / RMSE: squared error; RMSE is in the label's units
  • R²: share of variance explained (closer to 1 is better)

Classification

  • Accuracy = correct / total
  • Precision = TP / (TP + FP)
  • Recall = TP / (TP + FN)
  • F1: balance of precision and recall
  • AUC: separation across thresholds
  • Confusion matrix: TP, FP, TN, FN
Which metric? Missing a real case is costly (cancer screening): favor recall. False alarms are costly (flagging legitimate transactions): favor precision.

Language model components

  • Tokens: the chunks (words, sub-words, punctuation) a model reads and writes. Usage and cost are measured in tokens; one token is not always one word.
  • Transformer architecture: uses attention to weigh the relevance of each token to the others; consists of encoder and/or decoder blocks. GPT-style models are decoder-based and predict the next token.
  • Embeddings: numeric vectors that capture meaning; similar meaning gives nearby vectors. Used for semantic search, clustering, recommendations and RAG.
  • Context window: maximum tokens for prompt plus response combined.
  • LLM vs SLM: large models give broader capability; small language models are cheaper, faster, and can run on devices or at the edge.
  • Model families: chat/completion (text), reasoning models (spend extra tokens thinking before answering), multimodal (text plus image, audio), embedding, image generation, speech-to-text/text-to-speech, and open-weight or partner models in the Foundry catalog.

Configuration parameters

SettingEffect
System messageDefines role, tone, rules and format; sets behavior for the whole conversation.
TemperatureRandomness. Low (0 to 0.3) is focused and repeatable; high is creative and varied.
Top P (nucleus sampling)Samples only from tokens within a cumulative probability mass. Adjust temperature or top P, not both.
Max tokens (max completion tokens)Caps response length; too low truncates the answer.
Frequency penaltyReduces repetition of tokens in proportion to how often they have appeared.
Presence penaltyEncourages new topics by penalizing any token already present.
Stop sequencesText that ends generation when produced.
SeedImproves reproducibility of outputs (best effort).
Response formatPlain text, JSON, or structured output that follows a JSON schema.

Prompting, grounding and customization

  • Prompt engineering: clear instructions, role, context, examples. Zero-shot (no examples), few-shot (examples in prompt), chain-of-thought style step-by-step guidance.
  • RAG (retrieval-augmented generation): retrieve relevant data at query time and add it to the prompt. Fresh, citable, no retraining.
  • Fine-tuning: further train a model on labeled examples to change style, format or specialist behavior. Costlier and slower; it does not reliably add new facts.
  • Order of effort: prompt engineering, then RAG, then fine-tuning.

Compare candidates in the Foundry model catalog using capabilities (modalities, context window, tool support), quality benchmarks, latency, cost, region availability and licensing.

Deployment options

OptionWhen to use
Standard / Global Standard / Data ZonePay per token; flexible, good for variable or development workloads. Global and data-zone variants differ in where processing may occur.
Provisioned throughputReserved capacity for steady, high-volume traffic with predictable latency.
BatchLarge offline jobs that are not time-sensitive, at lower cost.

Deployment and access

  • In Foundry you choose a model from the model catalog and create a deployment (with a deployment name). Apps call the resource endpoint with that deployment name.
  • Authenticate with an API key or, preferably, Microsoft Entra ID (keyless, managed identity) with role-based access.
  • Capacity is governed by quota (tokens per minute / requests per minute). Deployment types include Standard / Global Standard (pay-per-token) and Provisioned throughput (reserved capacity, predictable latency).

2.1 Implement generative AI apps and agents by using Foundry

Foundry building blocks

  • Microsoft Foundry portal: web experience to explore the model catalog, deploy models, test in playgrounds, build agents, run evaluations and manage safety.
  • Foundry resource and project: the resource holds endpoints, keys, deployments and connections; a project organizes work for an app (agents, files, evaluations, connected resources).
  • Model catalog: models from Azure OpenAI (GPT family, reasoning, image, audio, embeddings), Microsoft, and partners/open-weight providers, with benchmarks for comparison.
  • Playgrounds: chat playground (test system message, parameters, grounding data), agents playground, image and audio playgrounds. Use "View code" to export SDK samples.
  • SDKs and APIs: Foundry SDK (azure-ai-projects), OpenAI-compatible client (Chat Completions and Responses APIs), REST. Auth with Microsoft Entra ID or key.

Build a chat app step by step

  1. Create a Foundry project; pick and deploy a model (a deployment is required before calling it).
  2. Test in the chat playground; write the system message; tune temperature, top P and max tokens; add few-shot examples.
  3. Add your data for grounding (RAG).
  4. Add content filters/safety settings; evaluate quality and safety.
  5. Call the endpoint from code: send messages with roles system, user, assistant (and tool for tool results). Use streaming to show tokens as produced and keep conversation history in the message list because the model itself is stateless.

RAG (grounding on your data)

  • Pipeline: chunk documents, create embeddings, store in a vector index (typically Azure AI Search), then at query time retrieve top matches, augment the prompt, and generate an answer with citations.
  • Azure AI Search supports keyword, vector and hybrid search plus semantic ranking.
  • Benefits: current and private knowledge, fewer hallucinations, traceable sources, no retraining.

  • Microsoft Agent Framework: open-source SDK for building single and multi-agent apps (successor to Semantic Kernel and AutoGen patterns).
  • Observability: tracing shows model calls, tool calls and latency for debugging. Evaluations measure quality (groundedness, relevance, coherence, fluency) and safety.
  • Governance: apply content filters, least-privilege access to tools, and human approval for high-impact actions.

Writing effective system and user prompts

  • System prompt: sets role, tone, rules, allowed topics, output format and what to do when unsure (for example "answer only from the provided context"). It applies to the whole conversation.
  • User prompt: the specific request for this turn.
  • Good prompts are specific about the task, give needed context, state the output format and length, add 1–3 examples (few-shot) when format matters, separate instructions from data with clear delimiters, and are refined by testing and iterating.
  • Prompts guide behavior but are not a security boundary; combine with content filters and grounding.

Python you should be able to read

Chat client with the Foundry SDK (install azure-ai-projects and azure-identity; sign in with az login for local development):

from azure.ai.projects import AIProjectClient
from azure.identity import DefaultAzureCredential

project = AIProjectClient(endpoint=ENDPOINT, credential=DefaultAzureCredential())
client = project.get_openai_client()          # OpenAI-compatible client
resp = client.responses.create(
    model="my-gpt",                           # your DEPLOYMENT name
    input="Explain RAG in one sentence.")
print(resp.output_text)
  • The project endpoint plus Entra ID credential identify and authorize the app. The model value is the deployment name. The same client also supports the Chat Completions API (client.chat.completions.create with a messages list of role/content dictionaries).

Single agent: create it, then chat with it:

agent = project.agents.create_version(
    agent_name="hr-helper",
    definition=PromptAgentDefinition(
        model="my-gpt",
        instructions="Answer HR policy questions politely."))

openai = project.get_openai_client()
conversation = openai.conversations.create()   # keeps multi-turn context
reply = openai.responses.create(
    conversation=conversation.id,
    extra_body={"agent": {"name": agent.name, "type": "agent_reference"}},
    input="How many vacation days do new hires get?")
print(reply.output_text)
  • Create and test the agent in the Foundry agent playground first, then write a small client that references the agent by name. A conversation preserves context across turns. Not every model supports agent tools, so choose a tool-capable model.
Trap. RAG does not retrain the model; fine-tuning changes the model; prompt engineering changes only the input. Agents differ from plain chat because they can plan and act through tools.

Respond to spoken prompts with a multimodal model

  • Deploy a model that accepts audio input (and optionally produces audio output). The app records or loads speech, sends the audio as part of the user message, and receives a text (or spoken) answer in one step, without a separate transcription call.

Python you should be able to read

# Text analysis (Azure AI Language)
from azure.ai.textanalytics import TextAnalyticsClient
from azure.core.credentials import AzureKeyCredential

client = TextAnalyticsClient(endpoint=ENDPOINT, credential=AzureKeyCredential(KEY))
docs = ["The staff were friendly but the room was dirty."]
print(client.analyze_sentiment(docs)[0].sentiment)       # positive / neutral / negative / mixed
print(client.extract_key_phrases(docs)[0].key_phrases)    # main talking points
print([e.text for e in client.recognize_entities(docs)[0].entities])
# Speech to text and text to speech (Azure Speech SDK)
import azure.cognitiveservices.speech as speechsdk

cfg = speechsdk.SpeechConfig(subscription=KEY, region=REGION)
recognizer = speechsdk.SpeechRecognizer(speech_config=cfg)   # default microphone
print(recognizer.recognize_once_async().get().text)           # one utterance

synth = speechsdk.SpeechSynthesizer(speech_config=cfg)        # default speaker
synth.speak_text_async("Welcome to the demo.").get()
Typical solution. Voice assistant = Speech to text (hear) → Language model or CLU (understand and decide) → Text to speech (speak).
Trap. Language service analyzes written text; Speech handles audio; Translator handles translation of text/documents; Speech translation handles spoken translation.

2.3 Implement AI solutions with computer vision and image generation by using Foundry

Outline focus. Interpret visual input in prompts by using a deployed multimodal model, create new visuals with generative models, and build a lightweight app with vision capabilities.

Visual input to a multimodal model

resp = client.responses.create(
    model="my-gpt",

img = client.images.generate(

    size="1024x1024")

  • Identification and verification are Limited Access features and require approval, reflecting responsible-AI concerns (privacy, fairness, consent).

Trap. Classification answers "what is in the picture?"; object detection answers "what and where?"; OCR answers "what does the text say?"; segmentation answers "which pixels belong to which thing?".

2.4 Implement AI solutions for information extraction by using Foundry

Outline focus. Extract information from documents and forms, from images, and from audio and video by using Azure Content Understanding in Foundry Tools, and build a lightweight application with extraction capabilities.

What Content Understanding is

Azure Content Understanding in Foundry Tools uses generative AI to turn documents, images, audio and video into a user-defined output format. It is part of the Microsoft Foundry resource. Output is either Markdown (good for search and RAG) or structured JSON that follows your field schema (good for automation and analytics).

Pipeline components

ComponentRole
InputsDocuments, images, audio, video.
AnalyzerThe core object: defines content extraction settings, the field schema and the model deployments. Prebuilt or custom.
Content extractionNormalizes content: OCR text, selection marks, barcodes, formulas, layout (paragraphs, sections, tables); speech transcripts and key visual elements for audio and video.
SegmentationSplits documents or video into logical parts (for example by document type or by scene).
Field extractionProduces key-value fields from your schema using three methods (below).
Confidence and groundingConfidence is a 0 to 1 estimate per field; grounding points to where in the source a value came from, so people can verify it.
Foundry modelsYou bring deployments of supported generative (and embedding) models that power field extraction and figure analysis.

Field methods

  • Extract: read values as they appear (documents only), such as dates and line items.
  • Classify: choose from predefined categories, such as call sentiment or document type.
  • Generate: create values freely, such as a summary of a call or a description of a scene.

Modalities

InputTypical outputs
Documents and formsText, layout, tables, figures (with descriptions), handwriting and annotations, named fields, chunked Markdown.
ImagesDescriptions and fields about visual content.
AudioTranscripts, conversation summaries, topics, sentiment (for example call-center analytics).
VideoSegments (scenes or topics), transcripts, per-segment descriptions and summaries.

Prebuilt analyzers to recognize

CategoryExamples
Content extraction (no LLM needed)prebuilt-read (basic OCR), prebuilt-layout (adds structure and tables), prebuilt-digitalParse (digital files)
Base analyzers (parents for custom ones)prebuilt-document, prebuilt-image, prebuilt-audio, prebuilt-video
RAG analyzersprebuilt-documentSearch, prebuilt-imageSearch, prebuilt-audioSearch, prebuilt-videoSearch: Markdown with layout, figure descriptions, summaries and embedding-ready chunks
Domain-specificprebuilt-invoice, prebuilt-receipt, prebuilt-idDocument, prebuilt-contract, tax forms such as prebuilt-tax.us.w2, mortgage and financial documents

Using the service

POST /analyzers/prebuilt-invoice:analyze      # run an analyzer on your content
GET  /analyzers/prebuilt-invoice              # read its definition and schema
PUT  /analyzers/my-invoice                    # create a custom analyzer from an edited copy
  • Analysis is asynchronous: you submit the content, then poll for the result (the SDKs wrap this in a long-running operation).
  • Start with a prebuilt analyzer; if fields differ, copy it and edit the schema, or build a custom analyzer from a base analyzer. Content Understanding Studio helps label data and improve custom analyzers.
  • Classification can route each document to the right analyzer (for example composed analyzers for tax, procurement and mortgage packets).
  • Use confidence scores for straight-through processing, sending low-confidence values to human review. Guardrails on the model deployment can block or annotate harmful content, so review warnings before automating.
  • Use the GA API version for production; preview versions add early features such as agentic mode.

Build a lightweight extraction app

  1. Create or use a Foundry resource and deploy the required models.
  2. Choose or create an analyzer (test it in the Foundry portal or Content Understanding Studio).
  3. In your app, send the file or URL to the analyze operation with the analyzer ID.
  4. Wait for completion, then read the Markdown or the JSON fields, confidence and grounding.
  5. Validate and store results; route low-confidence items for review.

Related services

  • Azure Document Intelligence: now described as part of Content Understanding; deterministic extraction (text, key-value pairs, tables) from structured and templated documents.
  • Azure AI Language: entities, PII and key phrases from plain text. Azure AI Search: indexes enriched content for retrieval; Content Understanding feeds it for RAG.
  • LLM structured outputs (JSON schema) can also constrain a model's response, but validate the results.
Choosing quickly. Mixed media or reasoning over fields → Content Understanding. Just a standard form → a prebuilt domain analyzer. Plain text entities or PII → Language. Text only, no structure → prebuilt-read; structure and tables → prebuilt-layout.

Common exam traps

  • Transparency vs accountability. Explaining how the system works and its limits is transparency; who answers for it and oversight is accountability.
  • Inclusiveness vs fairness. Designing for people of all abilities is inclusiveness; equitable outcomes across groups is fairness.
  • Reliability vs privacy. Safe, consistent operation is reliability and safety; protecting data is privacy and security.
  • Temperature vs top P. Both control randomness; change one at a time. Lower values are more deterministic.
  • Penalties. Frequency penalty scales with repetition count; presence penalty applies once a token has appeared at all.
  • Precision vs recall. Precision focuses on false positives; recall focuses on false negatives.
  • Regression vs classification. A number is regression, even if rounded; a named category is classification.
  • Clustering vs classification. Clustering has no labels; classification does.
  • Fine-tuning does not guarantee new knowledge. Use RAG for changing facts.
  • Function calling. The model suggests the call; your application executes it.
  • Read vs layout vs domain analyzers. prebuilt-read returns text; prebuilt-layout adds structure and tables; domain analyzers such as prebuilt-invoice return named fields.
  • Extract vs classify vs generate. Extract copies values from documents; classify picks a category; generate writes new values such as summaries.
  • Deployment name. Code passes the deployment name as the model value, not the catalog model name.
  • Face features (background): identification and verification need Limited Access approval.
